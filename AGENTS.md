# AGENTS.md

AR-assisted Capture The Flag app for Bsides Limburg, meant to make participants engage with the booths. Each booth has a printed QR code. Participants scan it, a flag appears on the code in AR, and tapping it shows a question. The booth staff tell them the answer; the participant types it in and the API returns a CTFd flag, which the participant submits on CTFd themselves. The app has no link with CTFd.

Source of truth for decisions and their rationale: [documents/spec/001-technical-direction.md](documents/spec/001-technical-direction.md). Original brief: [documents/files/ITF-005 AR for CTF.md](documents/files/ITF-005%20AR%20for%20CTF.md). If a change contradicts the spec, stop and ask; if a decision changes, update the spec in the same change.

## Stack

| Area | Decision |
| --- | --- |
| Mobile app | Flutter, Android first. iOS later (no Mac available; keep the code iOS-ready) |
| Architecture | MVVM with Riverpod, code generation style |
| Detection | `BoothDetector` interface: booth sightings with an optional pose. AR approaches are implementations behind it |
| AR approach | **Recommendation, pending the client** (spec 3.1, 3.7): marker-based AR without an AR SDK, entirely in Dart (`mobile_scanner` corners, homography, `CustomPainter`). Do not add an AR plugin or native AR code without asking |
| Backend | Go API on `net/http` (`ServeMux` method and path patterns, middleware as `func(http.Handler) http.Handler`) with PostgreSQL. No router framework (no Gin, chi, Echo) |
| Database access | `sqlc` on `pgx/v5`; migrations with `goose` (SQL files, embedded, run at startup). No ORM |
| Answer check | In the API: normalisation + fuzzy match against accepted answers, optional staff override code. No AI model |
| Scoring | CTFd, not integrated. Participants submit flags on CTFd themselves |
| Coach tooling | In the mobile app under a coach role. No separate website |
| Hosting | Docker Compose (API + PostgreSQL) on a laptop at the venue |

Not used, do not introduce: Unity, Vuforia, Firebase, Cloud Anchors / VPS, BLE beacons, a separate web admin, CTFd integration, LLMs for answer checking, participant accounts.

## Architecture rules

### Flutter app

- Layers: View (widgets) → ViewModel (Riverpod notifiers) → Repository → data sources (REST client, local cache, `BoothDetector`). Widgets never call data sources directly.
- Riverpod with code generation: `flutter_riverpod`, `riverpod_annotation`, `riverpod_generator`, `build_runner`. Use `@riverpod` annotations, not hand-written providers.
- Booth detection is accessed only through the `BoothDetector` interface (commands: `start`, `stop`; event stream: `sighted(BoothSighting)`, `lost(boothRef)`, `error`; `BoothSighting` = `boothRef` + scan token + optional pose). Implementations are swapped with a Riverpod provider override.
- ViewModels must work without a pose. The pose-less QR detector is the fallback for phones that cannot run the chosen AR approach.
- Payload parsing, token lookup, pose maths and smoothing filters are pure functions with unit tests.
- Offline tolerance: event booth data is fetched at start and cached. Scanning, rendering and showing the question work offline. Only the answer check needs the API; on failure the app keeps the answer and offers a retry (no background queue).
- Participants are anonymous: a random device ID is generated on first launch and sent as a header.
- Follow platform guidelines: Material 3 on Android, adaptive behaviour where iOS differs. Camera permission and "AR unsupported" are explicit flows.

### Backend

- Owns events and booths (scan token, question, accepted answers, flag, presentation). One question per booth.
- Accepted answers and flags never leave the API, except a booth's flag after a correct answer.
- Answer check: normalise (trim, lowercase, collapse whitespace, strip diacritics), then exact or Levenshtein match (≤1 up to 8 characters, ≤2 longer) against the accepted answers. Optional staff override code from configuration.
- Rate limit: 3 answer attempts per minute per device ID across all booths, in memory; `429` with `Retry-After`.
- Coach endpoints are authenticated. Participant endpoints are anonymous.

### QR codes and anti-cheat

- QR payload is `arctf://b/<token>`: a random 128-bit scan token per booth. It never contains the answer or the flag.
- The app caches only `SHA-256(token)` → booth, and never stores the token itself.
- When the detector provides a pose, the question can only be opened while the code is tracked and stable.
- Presentation is a field on the booth, so new presentations need no schema change.

## Working principles

### The Ponytail workflow (lazy senior dev mode)

Before writing any code, stop at the first rung that holds:

1. **YAGNI:** Does this need to be built at all?
2. **Reuse:** Does it already exist in this codebase? Reuse existing helpers and patterns.
3. **Stdlib first:** Does the Dart SDK, the Flutter framework or the Go standard library (`net/http`) already do this? Use it.
4. **Native platform:** Does an Android/iOS platform feature cover it? Use it.
5. **Existing deps:** Does an already-installed dependency solve it? Use it.
6. **Simplicity:** Can this be one clean line? Make it one line.
7. **Minimal diff:** Only then write the minimum code that works.

Execution rules:

- **Maximize Material 3:** Never hand-roll custom widgets when a Flutter Material 3 widget exists (e.g. `FilledButton`, `TextFormField`, `Card`, `ListTile`, `AlertDialog`, `SnackBar`, `NavigationBar`, `Badge`). Use `ThemeData`/`ColorScheme` instead of hard-coded colours and styles.
- **Ban AI slop and tropes:** No decorative glowing gradients, fake security badges or invented marketing copy. Keep the UI clean, high-contrast and functional.
- **No unrequested abstractions:** No boilerplate, layers, base classes or provider wrappers nobody asked for. The layers in "Architecture rules" are the required ones; do not add more.
- **Deletion over addition:** Boring over clever. Fewest files possible.
- **Shortcuts and ceilings:** Mark intentional simplifications with a `ponytail:` comment naming the ceiling and the upgrade path.
- **Non-negotiables:** Never be lazy about input validation at trust boundaries, security, or error handling that prevents data loss.

### Comments and documentation

- **No redundant comments:** No inline comments that repeat the code (e.g. `count++; // increment count`).
- **If a comment doesn't answer "how?" or "why?", omit it.**
- **Allowed comments:**
  - Doc comments on public APIs: `///` dartdoc in Dart, doc comments in Go.
  - High-level `why:` / `how:` context explaining non-obvious constraints.
  - Actionable `todo:` comments describing future improvements or known rough edges.
  - `ponytail:` comments documenting intentional MVP simplifications.
- **Style:** Short comments in lowercase (`// why: …` in Dart, Kotlin and Go). Capital letters only for multi-line contextual explanations.

### Functions and files

- **Single responsibility:** Functions, classes and widgets do one clear thing.
- **DRY:** Never duplicate logic; extract reusable widgets and utilities.
- **Clean code:** Zero dead code, unused imports or magic numbers (use named constants).
